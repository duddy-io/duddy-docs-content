Settings are per project, and they are what turns a design into a shippable app: the
name under the launcher icon, the package your store listing is registered against, the
permissions the app asks for, the keys it talks to services with.

Open them from the gear in the designer's header. Every page saves on its own **Save**
button — nothing is written as you type.

## Project

Four tabs, one Save. Everything here is required before a store build makes sense.

### Identity

| Field | What it does |
|---|---|
| **App name** | Shown under the launcher icon on the device. Letters and numbers only — no spaces or symbols. |
| **Package name** | The app's permanent identity, in reverse-domain form (`com.pictora.app`). **A build fails while this is empty**, and it can never be changed once the app is published to a store. |
| **Entry screen** | The first screen after the splash. |

<Callout type="warning">
  Choose the package name as if it is permanent, because it is. Google Play and the App
  Store both key a listing to it, and changing it later means publishing a second, unrelated app.
</Callout>

### Build

| Field | What it does |
|---|---|
| **Version code** | A whole number that must increase on every store upload. Stores reject an upload whose version code is not higher than the last. |
| **Version name** | What people read on the store listing — `1.0.0`, `2.4`, anything you like. |
| **Target SDK** | The Android API level the app is built against. Keep this at the newest level your app works on; stores enforce a floor. |
| **Min SDK** | The oldest Android version the app installs on. Min SDK 21 reaches roughly 99% of active Android devices. |
| **Target platforms** | Which of Android, iOS and Web this app is built for. Components and blocks are checked against every platform you keep on, so switch one off if you will never ship there — at least one stays on. |

### Assets

- **Launcher icon** — a square PNG with no rounded corners. Duddy masks it per platform,
  so bake nothing into the corners yourself.
- **Splash image** — fills the screen while the app starts.

### Danger zone

Archiving and deleting the project. Nothing here is part of an ordinary build.

## Theme

A project's palette lives here as named colours rather than hex codes scattered across
screens: components reference `primary`, `surface`, `onSurface` and the rest, so changing a
brand colour is one edit instead of a search through every screen.

You can keep several collections and switch a screen between them, build a palette out of
an uploaded image, or have the AI generate one. See [Themes and styling](/guides/designing/theme).

## Permissions

The list is assembled from the components you have actually used — place a
[LocationSensor](/components/sensors) and its location permissions appear here; delete it
and they can be removed. Refresh re-reads the screens.

Prefer a picker over a permission wherever both exist: `ImagePicker`, `FilePicker`,
`ContactPicker` and `BarcodeScanner` need no permission on either platform, because the
system UI does the asking for you.

<Callout type="info">
  Ask for a permission in your logic at the moment it is needed, not on app start. Both stores
  review this, and users decline a prompt that arrives with no context.
</Callout>

<Callout type="info" title="The list follows your components">
  A build declares what your components require, which is the list on this page. To drop a
  permission, drop the component that needs it.
</Callout>

## Manifest

A raw editor for the Android manifest entries Duddy cannot infer — extra `<meta-data>`, an
exported activity, a queries block. What you write here is spliced into the `<application>`
element of every Android build, after everything Duddy generates for you: the permissions,
the launcher activity, and the entries your components declare for themselves.

<Callout type="info" title="Android only">
  iOS has no manifest, so this page changes nothing in an iOS build. Keep the snippet to
  elements that belong inside `<application>` — a stray `<uses-permission>` here fails the
  manifest merge, and the build log says so.
</Callout>

## Keystore

The signing key your Android release builds are signed with. Upload a `.jks` or
`.keystore` file and select it, or leave the page alone — if no keystore is set, Duddy
generates one when you build.

<Callout type="danger" title="Keep your keystore">
  Google Play ties an app to the key it was first uploaded with. Upload your own keystore
  and keep a copy of it somewhere safe: without it you cannot ship an update to a published app.
</Callout>

## Deep links

Let a link or a file open a screen inside your app. Each row is a screen, a type and a
value:

- **Host** — a link that opens the screen. Use your app's own scheme
  (`pictora://receipt`) for a link that always opens the app, or a web address you own
  (`https://pictora.app/receipt`).
- **File** — a file type, given as a MIME type such as `image/png`, so your app is offered
  as a way to open files of that kind.

Add one row per screen you want reachable. Every build of your app carries these rows, and a
[live test](/getting-started/build-the-app#test-it-live-on-a-device) app too: the screen
opens with the link — or the opened file's address — as its start value, so its blocks can
read what opened it. A file row takes a family as well as a single type (`image/*`).

<Callout type="info" title="Web links on phones">
  On Android 12 and later, a web link opens in the browser until the phone's owner allows
  your app for that domain under the app's "Open by default" settings; older Android
  versions ask which app to use. iOS opens web links in an app only through Associated Domains,
  which need a verification file on your own domain, so web rows are left out of iOS builds —
  use your app's scheme for a link that must open the app on both. iOS also names file types
  by identifier rather than MIME type, so a file row reaches an iOS build only for the common
  image, video, audio, text and document types; one it does not know is left out, and the
  build log names it.
</Callout>

## Integrations

Project-level keys and IDs. These are read by the platform before any component runs,
which is why several components share one field rather than each carrying its own.

| Group | Holds |
|---|---|
| **Google** | Maps API key, Google app ID. A missing Maps key builds fine and draws a blank grid. |
| **Firebase** | The project behind Auth, Realtime Database, Firestore, Storage and Cloud Messaging. Pick one from a connected Firebase account and Duddy pulls `google-services.json` and `GoogleService-Info.plist` for you, or upload the two files by hand. |
| **Pixabay** | Royalty-free photos and illustrations in the asset picker. |
| **Ads** | AdMob app ID, Meta app ID and client token. Without an AdMob ID, builds fall back to Google's official test unit. |
| **In-App Purchases** | The product and subscription IDs sold through the App Store and Play Store. |

<Callout type="danger" title="Firebase has no fallback">
  A project using a Firebase component with no config file fails the build with an explicit
  error rather than shipping something that silently cannot connect.
</Callout>

Account-level connections — Figma, Pixabay, Firebase and Apple Developer — are set once
for your whole account under **Integrations** in the dashboard. See
[Figma](/integration/figma) and [Apple](/integration/apple).

## Collaboration

Invite people by email address. Three levels:

| Role | Can |
|---|---|
| **Read only** | View screens and preview the app. |
| **Read & write** | Edit screens, logic and assets. |
| **Admin** | Everything above, plus manage collaborators. |

Everyone in a project edits the same canvas live — cursors, selections and property
changes appear as they happen, with no merge step. See
[Working together](/guides/collaboration/teamwork).

## About

The listing for the project: cover image, name, one-line pitch, category, tags, licence
and a Readme written in Markdown. Licences on offer include the Duddy License, MIT,
Apache 2.0, GPL v3, BSD 2/3-Clause, MPL and Creative Commons.

## Hosting

The control surface for a web build that is online: the live link, what it costs per
period, and what it has cost so far. A build is not a publish — building the web app
stages it, and **Update live app** is what moves it. Web builds, and with them hosting, are
[coming soon](/getting-started/build-the-app#web-builds-and-hosting).
